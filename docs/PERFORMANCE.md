Hardware: Intel Core i9-13900HX (24 cores / 32 logical CPUs), 32 GB RAM (31.74 GiB reported usable), NVIDIA GeForce RTX 4060 Laptop GPU, Windows 11 Home 10.0.26200. NVIDIA driver: 32.0.15.9174. Chromium 153.0.8010.12 selected ANGLE Direct3D11 on the NVIDIA GPU. Canvas/viewport: 1440×1000, density 1, headless.

The actual match reached **180 active seconds**, ended by time, and registered automatically with 7 points / 100 health. There were 10,799 measured frame intervals and no uncaught page exceptions.

## Reproduction

Install the locked dependencies and Playwright Chromium, then run `npm run profile`. This builds the optimized Vite **profile** mode and launches an isolated localhost preview on port 5176. The script closes its own browser and preview process when finished. Run `npm run build` afterward to restore the normal delivery build. Never deploy the profile build.

The profile observer is enabled only by `import.meta.env.MODE === 'profile'`. It exposes read-only state, timing arrays and numeric resource counts. It has no time advance, health, position or entity setters. Normal builds remove the observer. The workload uses the actual ticker, simulation, rendering, audio, keyboard handlers and mock registration. A keyboard captain aims at living enemies and fires the three batteries; it does not replace gameplay rules. Match settings are 180 seconds, a 30-second spawn interval and layout seed 3. This is a repeatable workload, not a worst-case one-second-spawn stress test.

## Measurement definitions

- **FPS:** 1000 divided by the mean interval between consecutive active game callbacks. Paused time and asset loading are excluded. This is measured callback cadence, not a guarantee of visible presentation on a physical display.
- **Frame p95/p99:** nearest-rank percentile of those actual `performance.now()` intervals. These include scheduling and rendering overhead between updates; simulated delta is never used as a performance measurement.
- **Update p95:** time spent inside the game's simulation and visual-update callback. The Pixi renderer runs separately, so this is not complete CPU/GPU frame cost.
- **Entities:** ship, projectile and simulation-effect peaks observed each active frame, with one-second samples retained. Decorative sprites and wake ripples are outside these simulation counts.
- **Memory:** Chromium renderer JS heap after explicit `HeapProfiler.collectGarbage`, alongside `Memory.getDOMCounters`, active scene/canvas and audio-source counts. This does not measure total browser/process RAM, GPU texture memory, decoded native audio memory or other renderer/worker processes.

One warm scene initializes the shared texture/audio caches before the baseline. After the complete three-minute match, five more cycles enter gameplay, sail/fire for five real seconds, exit and settle for two seconds before GC and collection. Weak references count surviving simulation objects after GC without retaining them. The audio resource observer is bound directly to the app's SoundManager so its archive does not capture a scene's closure. Measurements intentionally retain numeric timing arrays in the profile build; small heap growth from those archives is not scene retention. Shared decoded audio buffers and Pixi Assets textures remain cached for subsequent matches. Live scenes, surviving simulations, canvases and playing audio must return to zero.

The JSON evidence contains hardware/browser/renderer information, the complete balance snapshot, per-frame intervals, per-second entity counts and each lifecycle measurement. The driver also observes uncaught page exceptions. If the match ends before 180 active seconds, it saves incomplete evidence and fails instead of claiming a three-minute measurement.

## Interpretation limits

The automated run uses headless Chromium at 1440×1000 and device density 1. Record the renderer string: a software renderer is not evidence of performance on the laptop's GPU. The target is 60 FPS; a passing functional test or a simulated phone viewport does not prove that target on a physical phone. Browser visibility, power mode, competing processes, refresh rate and graphics backend affect results. No minimum-FPS guarantee is asserted from this reference workload.

On Windows the driver requests `--enable-gpu --use-angle=d3d11`; elsewhere it requests `--enable-gpu`. It still records the actual backend, since these flags cannot guarantee hardware acceleration. An initial diagnostic attempt used Chromium's default SwiftShader backend and averaged about 12.5 callbacks/second over 20.9 active seconds; it ended in death. A subsequent RTX attempt ran at about 60 callbacks/second but its pilot kept firing into the island corner and also ended early. Neither attempt is a three-minute result. The pilot now checks clear rays within an enemy hull's angular width before aiming; no gameplay balance was changed.

## Texture cleanup review

The 8 October rerun follows explicit destruction of arena-owned atlas crop textures on exit/error. Shared cached source textures remain intact. The profile now measures the atlas source resize listeners directly: warm baseline, post-match and all five exits report exactly 1, representing its cached base texture. No per-scene crop listeners remain after exit. This supplements DOM listener and simulation counts, which alone did not observe atlas emitter retention.
